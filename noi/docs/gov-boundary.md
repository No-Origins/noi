# Governance boundary and deployment limits

`noi_gov::Authorizer` is the only governance decision interface used by registry operations. It receives a trusted actor, action, resource UUID/path/revision/scope references and the concrete operation intent. For relation edits both endpoints are resources; for renames both old/new locations are resources. Proposals include the scope system. Updates include the proposed definition, declared compatibility evidence and affected consumers. Decisions are `allow` with a nonblank reference, `deny`, or `approval-required`. Only allow commits. Exceptions in storage/validation or a missing authorizer fail closed. Approval-required is a refusal to write, not a queued approval workflow.

All successful mutations append the decision, actor and before/after or relationship/release payload in the same transaction. Denied/approval-request attempts are not registry events; a production Governance adapter must record those governance decisions in its own audit system. Registry history is retained, with SQL privileges and triggers preventing runtime update/delete. Read access is authorized too; an all-registry projection is denied if the authorizer does not permit every included resource. There is no row-filtered multi-tenant projection yet.

`LocalDevelopmentGrant` is deliberately small: one explicit subject and a dot-segment-bounded namespace. It grants all actions within that namespace. It is not a policy engine and must not be used for hosted/shared deployment. The CLI subject comes from the trusted local shell. The server uses this configured capability, binds only to loopback, checks browser Host/Origin, and offers only read routes. It does not accept client-provided actors. Browsers receive no database credentials and no CORS grant.

Invariants stores only `authority_scope` structural references to live system merons. Policy inheritance, authority delegation, roles, approval resolution, credentials, policy activation and revocation semantics belong to Governance. The seeded release-approval meron is a provisional policy identity with no executable grants. Registering or editing it cannot change the development grant.

## PostgreSQL access

The migration keeps the schema outside `public`, revokes public/anon/authenticated access, enables RLS on every table in `mer` and creates policies for `noi_mer_runtime` only. Do not add `mer` to Supabase exposed schemas. Since 7 Nov (step 3) the runtime role can log in on this Mac, with a password set as a SCRAM verifier by `infrastructure/supabase/runtime-logins.py` and kept only in the owner-only `noi/mero.local.env`; Governance's `noi_gov_runtime` likewise, in `noi/governance.local.env`. Do not copy the development postgres password into a production environment. Use the owner only for migrations, not normal runtime connections. TLS and least-privilege provisioning are operator responsibilities for a hosted database.

Runtime role privileges are restricted by table: no DELETE on merons/releases/identifiers/events/generations, no UPDATE on relationships/events/identifiers/generations, and no TRUNCATE. Superusers and table owners can bypass the protections. A trusted backend login can still execute structural SQL without Governance; this is explicitly **not** a database-enforced governance system. Expose domain operations through adapters, never direct database tools for agents.

The synchronous trait intentionally supports a deterministic local adapter now. A production network-backed Governance integration should resolve authorization with bounded timeouts, provide immutable decision references bound to the exact intent/revisions, handle policy invalidation, and recheck at commit where needed. Do not add a permissive error fallback. The current registry holds a global mutation lock while calling the adapter, so network latency would block writes. Design that integration before scaling.

The shared Supabase infrastructure does not widen the registry role or Governance authority. Other applications require their own backend roles and explicit interfaces to registry operations. Administrative migration metadata is isolated in `mer_migrations`, outside runtime data and API-exposed schemas.

## Implemented minimum local policy

Superseded on 2026-11-07 (step 3): Mero asks Governance's server about every request (see "Mero asks Governance" in `architecture.md`); `ScopedAuthorizer` remains only as a test stand-in. It provided explicit observer/contributor/maintainer permissions and governance-scope inheritance from a trusted, versioned operator configuration. All resources must be covered; descendant grants cannot widen inherited restrictions. Unknown identities/scopes fail closed. Contributor mutations beyond proposing return approval-required. A maintainer reviews and executes with current revisions; no persisted approval request is created. Every allowed decision records policy ID/revision and a unique reference. See `specifications/GOV-001.md` and `specifications/reconciliation.md`. The shell-selected subject is still a local trust boundary, not remote authentication.
