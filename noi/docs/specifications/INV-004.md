# INV-004 · Lifecycle — provisional implementation profile

Meron: `proposed → registered → active → deprecated → retired`.

Release: `planned → experimental → stable → deprecated → unsupported`.

Transitions are adjacent and forward only. Same-state operations, skips and reversals are errors. Optimistic revisions are required for meron/release transitions and meron definition changes. Retired merons cannot be edited. There is no delete or automatic archival state. Lifecycle operations record before/after and Governance decisions atomically.

Meron and release states are independent. A meron can remain active while releases become deprecated. Release creation requires an admitted (`registered`, `active`, `deprecated`) independent meron. Stable releases cannot use prerelease versions. Inherited merons own no releases. Effective release follows `contains` to the nearest independent ancestor and chooses its highest stable generation/semantic version; no stable release means no effective release. An independent boundary never silently falls through to its parent.

The seeds are proposed, unreleased reference definitions. NOI is independent; all other reference merons inherit. No Generation 01, stable status or publication is implied by seeding.
