Let's proceed with **XEC-004 v0.1.0 — Entity Lifecycle**, the fourth working specification under XEC.

Its purpose is to define how entities are created, registered, evolved, deprecated, and retired while preserving identity and traceability.

## 1\. Define the entity lifecycle

I propose six foundational states\:

**Draft**

Defined but not registered for operational use

**Registered**

Recognized with a canonical identity

**Active**

Available for intended use

**Deprecated**

Still identifiable, but discouraged for new use

**Retired**

No longer supported for operational use

**Archived**

Retained for history, audit, and reference

The primary progression; exceptions, such as restoring a deprecated entity, require explicit transition rules.

An important refinement: **registration and activation are different events.** An entity can have a canonical identity without being approved for use.

## 2\. Separate lifecycle, releases, and generations

These are three independent dimensions.

| Dimension | Describes | Example |
|--------|--------|--------|
| Lifecycle state | Operational standing | `active` |
| Release version | Particular published revision | `1.2.0` |
| Generation | Architectural lineage | `01` |

An active entity can have several historical releases. A deprecated entity may still be available in older supported releases. A new architectural generation can coexist with the previous one.

Consequently, we must not treat `deprecated` as a version number or `02` as a lifecycle state.

## 3\. Define lifecycle transitions

XEC specifies which transitions are structurally valid. XGA determines who may perform them.

| Transition | Structural condition |
|--------|--------|
| Draft → Registered | Valid identity and entity contract |
| Registered → Active | Applicable contracts and readiness requirements satisfied |
| Active → Deprecated | Deprecation reason and migration guidance |
| Deprecated → Retired | Retirement requirements satisfied |
| Retired → Archived | Historical record preserved |
| Deprecated → Active | Reinstatement criteria satisfied |

The table defines candidate transitions, not automatic authorization. XGA may require different approvals for each transition.

## 4\. Entity lifecycle contract

```yaml

entity:
  id: no.xei
  name: XEI

lifecycle:
  state: active

  release:
    mode: independent
    generation: "01"
    version: 0.1.0

  history:
    created_at: null
    registered_at: null
    activated_at: null

  successor: null
```

This is an illustrative schema. Since XEI's operational registration and release haven't yet been established, the lifecycle state and version shown here are examples rather than verified records.

I would keep the actual event history in a separate append-only record instead of repeatedly overwriting lifecycle history fields.

## 5\. Establish five lifecycle invariants

1. A published canonical ID must never be silently reassigned to a different entity.
2. Every lifecycle transition must be attributable and traceable.
3. An independently released entity maintains its own release history.
4. Architectural generations must preserve an explicit lineage relationship.
5. Retirement must not erase historical identity or invalidate the audit trail.

These rules will allow human and AI agents to improve the system without losing its history.

## 6\. The key architectural distinction

**An entity may evolve without changing its identity.**

For example\:

ILLUSTRATIVE EVOLUTION

## `no.xei`

**Generation 01**

v1.0.0 → v2.0.0

**Generation 02**

v0.1.0 → v1.0.0

The enduring identity remains `no.xei`; its implementation architecture and releases change.

A breaking change does not automatically require a new generation. Generations should be introduced only when maintaining a distinct architectural lineage is justified.

### Next recommendation

We should now define **XEC-005 — Entity Evolution &amp; Compatibility**\.

XEC-004 describes the states of an entity. XEC-005 would describe how to evaluate actual changes: whether they're compatible, whether they need a release, how migration works, and when a new generation is justified.

That distinction will be especially valuable for XEI's agent-driven evolution.

We should keep all four specifications provisional until we've tested them together against real entities and reviewed their governance implications through XGA.
