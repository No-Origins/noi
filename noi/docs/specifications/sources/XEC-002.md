# XEC-002

**Entity Type System**

## 1\. Formal classification model

Every registered entity has a primary type. It may additionally declare a subtype, contextual roles, and capabilities.

```yaml
classification:
  type: rule
  subtype: policy
  roles:
    - release-governance
  capabilities: []
```

These fields have distinct meanings\:

| Dimension | Definition | Cardinality |
|--------|--------|--------|
| Type | Fundamental classification | Exactly one |
| Subtype | Specialized classification | Zero or one initially |
| Role | Responsibility in a context | Zero or more |
| Capability | Supported operation or behavior | Zero or more |

A capability declaration does not imply permission. XGA remains responsible for authorization.

## 2\. Seven foundational types

| Type | Formal classification criterion |
|--------|--------|
| `system` | Coordinates constituent elements to produce defined outcomes |
| `agent` | Can participate in purposeful actions, whether human or artificial |
| `component` | Provides reusable functionality through a defined composition boundary |
| `token` | Represents a named semantic value or reference |
| `rule` | Expresses an evaluable constraint, requirement, or directive |
| `contract` | Defines a structured set of conformance requirements, obligations, or interfaces |
| `document` | Preserves and communicates managed information |

These are **provisional foundational types**, not a declaration that the ontology is complete.

A specification such as XEC-001 can therefore be a `contract` entity, while a PDF or Markdown file publishing that specification can be a `document` entity referencing the contract.

## 3\. Subtype inheritance

I propose three requirements\:

1. A subtype must satisfy all mandatory requirements of its parent type.
2. A subtype may add constraints and specialized fields but cannot silently contradict its parent.
3. Changing an entity's subtype must trigger validation of its existing relationships and applicable contracts.

For example, `policy` inherits from `rule` but adds governance-specific requirements defined through XGA.

## 4\. Introducing new entity types

A new top-level type should require evidence that existing classifications are insufficient.

**Proposed registration workflow**

1. Submit a proposed type definition and classification criteria.
2. Compare it against all existing types and subtypes.
3. Demonstrate a distinct identity or conformance boundary.
4. Validate its compatibility with XEC-001.
5. Obtain the approvals required by XGA.
6. Register the approved type with a traceable specification version.

## 5\. What remains unresolved

Before XEC-002 becomes stable, we still need to test whether the proposed categories are sufficiently exclusive, particularly the boundaries between `system` and `component`, and between `rule` and `contract`\.

We also need to distinguish **entity type inheritance** from **contract applicability**\. An entity may need to satisfy multiple specialized contracts without acquiring multiple primary types.

That is an important extensibility requirement for agent-driven evolution.

## Next milestone

I recommend moving to **XEC-003 — Entity Relationships**, where we formally define relationships such as\:

`contains`, `depends-on`, `implements`, `conforms-to`, `governed-by`, and `owned-by`\.

This is a natural progression because identity and classification tell us what an entity is, while relationships tell us how the entire XEI universe is constructed.

We'll keep XEC-002 at draft status until its boundary tests are complete, rather than prematurely freezing the registry.
