## Trust and policy activation

The trusted operator loads a JSON `GovernancePolicy` containing an ID, positive revision, known governance scopes and subject assignments. Loading a policy is an administrative action; registering a rule/policy meron does not activate it. Policy changes must be operator-reviewed and versioned. The policy file is external trusted configuration, not writable through registry operations. Governance core remains independent of Invariants and PostgreSQL.

The CLI accepts `--governance-policy FILE --actor SUBJECT` or `NOI_GOVERNANCE_POLICY` / `NOI_ACTOR`. It rejects combining a policy with the unrestricted `NOI_DEV_ACTOR` capability. An invalid policy fails before any operation. Without an authorizer the registry continues to deny all domain access. These subjects come from the trusted local shell; they do not authenticate remote users. Protect the policy file and database credentials from untrusted processes.

## Permission rules

| Role | Read | Propose a definition | Update, breaking evolution, rename, lifecycle, relationships, releases |
| --- | --- | --- | --- |
| observer | Allow | Deny | Deny |
| contributor | Allow | Allow | Approval required |
| maintainer | Allow | Allow | Allow after Invariants validation |

Non-breaking claims also need maintainer review because invariant-check strings are not independently evaluated. A policy definition can be proposed but confers no permissions. Invariants lifecycle and database constraints apply even to a maintainer.

## Scope resolution

Scopes are UUIDs, with optional explicitly configured parent UUIDs. No namespace or containment inference is permitted. Unknown scopes, unknown subjects, nil/duplicate scopes, missing parents, cycles and duplicate subject/scope assignments fail closed. Assignments inherit downward. Where a subject has assignments at several ancestors, the most restrictive role wins; a child assignment cannot silently widen its ancestor's permissions. Removing a parent link or changing a grant is a trusted policy administration action, not runtime delegation.

Every resource must resolve an assignment. For relation edits this includes both endpoints; renames cover both locations; proposals cover the prospective meron and its authority system. A read of the full explorer snapshot requires access to all included resources; no row-filtered projection is introduced.

## Review and audit

Approval-required aborts the transaction. The contributor hands the concrete proposal, target UUID, expected revision, evidence and migration plan to a scoped maintainer. The maintainer reviews and executes the operation under their own local identity. Current revisions are rechecked by the registry. There is no approval queue or approval record that automatically retries the original action. This avoids implying a persistent approval workflow or separation of duties enforced against an operating-system administrator.

Successful decisions have unique references and include policy ID/revision. The existing atomic change event records the executing actor, decision, before/after records, compatibility evidence, migration plan and affected consumers. Earlier proposal events retain the contributor's identity. Denied/approval-required attempts produce no registry change event; durable attempt auditing remains future Governance work. Policy content history is operator-managed; a referenced revision must not be reused for different policy contents.

## Run locally

Copy `examples/governance-policy.example.json` to an operator-controlled local file and replace the scope UUID with the actual `noi` UUID (get it using the existing local development command). The example UUID is explicitly illustrative and grants no access to the real registry until replaced. Do not commit machine-specific assignments.

```sh
unset NOI_DEV_ACTOR
export NOI_GOVERNANCE_POLICY=/absolute/path/to/governance.local.json
export NOI_ACTOR=design-agent
scripts/noi-dev list
scripts/noi-dev propose /absolute/path/to/token.json
# A contributor cannot register it:
scripts/noi-dev transition TOKEN_UUID 1 registered
# After reviewing the definition, the operator executes as the maintainer:
NOI_ACTOR=local-maintainer scripts/noi-dev transition TOKEN_UUID 1 registered
NOI_ACTOR=local-maintainer scripts/noi-dev transition TOKEN_UUID 2 active
```

For a breaking/unknown update, `compatibility` must include `migration_plan`, for example `Review dependent button behavior, migrate consumers, and retain the prior release until rollout completes`. A justified statement that no migration is necessary is also valid; Invariants validates presence and size, not whether the plan is true or has been carried out.

Run the opt-in PostgreSQL integration test to exercise the full contributor/maintainer workflow in a disposable database; it leaves the development registry's definitions untouched.

A machine-specific `governance.local.json` has been created for this development registry using its real root UUID. It is excluded from Git and has owner-only read/write permissions. To use it, set `NOI_GOVERNANCE_POLICY` to that file and select `design-agent`, `observer` or `local-maintainer` as `NOI_ACTOR`. The existing explorer process is not automatically switched to a different capability when this file is created.
