# INV-005 · Evolution and compatibility — provisional implementation profile

Every definition update supplies its expected revision and explicit compatibility evidence: impact (`non-breaking`, `breaking`, `unknown`), nonblank rationale and check descriptions. A non-breaking claim needs at least one named evaluation/check. The runtime does not certify those assertions. Unknown/breaking changes request Governance `evolve-breaking`; non-breaking changes request `update`.

The registry calculates transitive incoming `depends-on`/`implements` consumers and includes them, current definition and proposal in the authorization intent and audit event. Semantic field edits do not silently assert consumer compatibility. UUID and primary type remain immutable; path changes use a distinct rename operation preserving aliases. Scope reassignment and release-mode conversion are not implemented.

A release has a semantic version and positive generation number. First use of a generation records an immutable architectural rationale; later releases reference it. Release data is independent of meron revision. No generic semver-based compatibility oracle, mandatory new generation for every breaking change, automatic migration, consumer approval store or invariant execution is claimed. Those rules require Governance and the missing original evolution specification.

Reconciliation status: see `reconciliation.md` and `sources/INV-005.md`. This remains an implementation profile; deferred draft features are not implied.

The local workflow additionally requires a nonblank `migration_plan` (at most 8,000 bytes) for `breaking` or `unknown` impact. A justified no-migration decision is permitted. This consideration is recorded in authorization intent and audit history; it does not certify migration completion. Under GOV-001, all updates require maintainer execution because supplied check descriptions are not executed.
