## Minimum workflow agreement

A contributor proposes a token and a button. A maintainer reviews the stored definition, registers and activates the token, and records the button dependency. A contributor's transition, relationship edit, update or release request returns approval-required without changing data. The maintainer reviews the proposed operation and executes it using the current expected revision. A breaking token update requires a migration plan and records the dependent button in the event. The read-only explorer projection reflects the committed result.

Approval here means a trusted local maintainer reviewing and executing the operation. There is no persistent approval inbox, transferable approval token or remote authentication. A contributor cannot approve themselves through the authorizer; someone with shell/database/configuration administration is inside the trusted operator boundary and can select any local identity. Remote adapters must authenticate identities before invoking this boundary.

## Remaining specification work

Formalize type-specific invariants and conformance predicates; accountable ownership and authority delegation; readiness and deprecation evidence; archival/reinstatement semantics; supported release lines, migration acknowledgments and generation coexistence. These are explicit gaps, not inferred implementation features. See `GOV-001.md` for the minimum executable rules and `../outstanding.md` for the wider backlog.
